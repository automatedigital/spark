## Implementation and ownership

- Retain schema-v1 `/api/conversations/{session_id}/recovery` and all legacy routes.
  SessionDB reads lineage, bounded history, durable cursors, run projections and
  pending decisions in one real SQLite read transaction using its reentrant lock.
- Independently fence the process journal epoch/sequence and stream identity/
  revision, then confirm the durable snapshot. Three assembly attempts maximum;
  continued movement returns 409 `reconcile_again`. No recovery lifecycle writer.
- Stream text is bounded to 64,000 characters, including offset requests. History
  defaults to 80 rows with a 200-row accessor maximum. Projection revision covers
  history/decisions as well as run projections. Durable and delivery cursors stay
  distinct; neither substitutes for a Task, Run, goal or execution identity.
- Preserve SP01 accepted-but-uncertain execution after process loss, durable
  approvals and compression lineage. Never redispatch a prompt/tool to rebuild UI.
- Consume one guarded response instead of status/history/plan/outcome/decision
  fan-out. Restore history before the live tail; reject older active revisions.
  Reconcile inactive reducer state without a second history request. Retain owner,
  session-generation and backend/profile fences and legacy history pagination.
- Keep a cached transcript visible during reconciliation. Confirmed stalled work
  and failed reads retain the existing two-second recovery cadence, now using
  the single response. Ordinary opens/explicit reconnect use one recovery request.

No schema/config/lockfile/generated manifest/production bundle changes. No
provider metadata/runtime_provider, Settings/ModelPicker, cron, terminal or

## The three blockers

### Recovery card and actual backend state

The original five-second stalled fixture could finish before navigation. A
controlled six-second open delay reproduced this on baseline and candidate:
backend `turn_active=false`, `state=not_found`, persisted outcome `completed`.
Candidate then failed the unchanged 15-second card assertion; baseline could
lose the Running row first. A completed backend correctly has no reconnect card.
The fixture now uses a 60-second synthetic stall, verifies
`turn_active=true/state=stalled` before opening, and restarts its backend within
that fixture lifetime in the recorded flows. The UI deadlines are unchanged.

Separately, a real ownership defect cleared confirmed recovery when the same
snapshot adopted a compressed session ID. Move that reset to the panel's actual
session-reset callback. A deterministic fixture commits real SQLite compression
while recovery is held, returns the real endpoint response, adopts the child ID
and checks retained tail/card. Reinstating the old active-ID reset reproduces the
15-second card failure; the fixed source passes.

Holding work through real restart also exposed two recovery defects: synthetic
transport signals were deduplicated using the journal's unchanged cursor, and
inactive recovery did not retire the reducer. Transport signals now neither
advance nor deduplicate the journal cursor; inactive snapshots reconcile the
reducer from the already supplied history. The proxy can keep EventSource open
across backend loss, so confirmed stalled/failed recovery retains a rate-limited
fallback instead of depending solely on a transport error. Focused regressions
cover same-cursor reconnect, cursor preservation, foreign snapshots and inactive
recovery without a legacy history request. The restart test also asserts a
visible unknown-tail label: append it after history replacement and show it on
the recovery card, rather than relying on a note inside collapsed work history.

### Two 240-message histories

The unchanged 30-second live-tail assertion fails on the prepared SP01 archive
and the pre-fix candidate. Actual candidate recovery responses contain the correct
live tail and 80 saved rows. Captured viewport: scrollTop 121, scrollHeight 11671,
clientHeight 533, virtual indices 0–11 (saved history starting at row 160).
SP01's 50-row page similarly stays at the top (scrollHeight 8221, starting row 190).

A bounded scroll trace showed the initial clamp settling with zero timeline rows
while the loading skeleton rendered. When real rows mounted, a layout scroll
was classified as user detachment. The fix keeps the pending jump until
real rows/messageList exist, then requires the measured final row and stable
height before settling. A warm-return trace found another concrete path: hydration
replaced rows at equal count, cancelled the earlier scheduled jump, and the ordinary
stream-tick branch marked the jump complete without calling the clamp. Pending
jumps now always use the measured clamp, regardless of count changes. This
preserves the virtualizer, bookmarks and detached readers. No live-tail assertion, fixture size or timeout was weakened.

The final long fixture passes five switches, two active histories, live-tail
visibility, delayed-old-response rejection, explicit reconnect, refresh and
compression-during-fetch; all measured switches use one recovery request and
zero conversation POSTs.
