## Implementation

- Retains the existing LRU, count cap and bounded preparation/runtime workers.
  Adds `dashboard.agent_cache_idle_seconds` (1800) and
  `dashboard.agent_cache_context_bytes` (64 MiB). Zero disables the corresponding
  new limit. Optional environment overrides are documented in config metadata.
  Existing configs use additive defaults; no config-version migration is needed.
- Eviction checks idle time, count and estimated retained context. Live root
  ownership, attached worker DBs, children, warm workers, blocking approvals,
  pending decisions and durable live children protect entries. Compression
  ancestors are included in durable ownership checks. Protected entries can
  exceed targets; uncertain durable ownership prevents eviction.
- Idle entries are swept on cache use and by one sequential lifespan maintenance
  task, at most every 30 seconds. It uses existing blocking workers and is
  cancelled with server startup tasks. Idle disposal calls the agent's existing
  `close()` lifecycle. SP03's physical worker-owned DB leases are unchanged.
- Helper-owned additive SQLite revision tables/triggers certify a profile,
  database/session generation and transcript revision. Inserts, same-length
  edits, deletions, moved messages and backdated inserts invalidate stale reuse.
  Context metadata and effective route signatures must also match. This follows
  the existing optional-helper schema pattern, without editing SessionDB's
  numbered migrations or retaining a connection in the idle cache.
- An unchanged warm request skips full-history hydration. A verified warm send
  reuses its immutable durable prefix and consumes the stamp before execution.
  Accepted prompts remain outside past history. External writes, compression,
  profile changes, session recreation and route changes invalidate reuse.
  Warming cannot replace a child-owned agent on a changed route.
- Cache metadata follows LRU entries; recent warm bookkeeping is capped at 256.
  Warm queue/running admission remains bounded by SP03's existing pool, including
  cancellation and background handoff. No new pool, dependencies, lockfile,
  generated manifest or web_dist changes are committed.

The byte estimate includes selected Python history/prompt/tool objects and UTF-8
serialization headroom, deduplicating shared objects within an agent. It excludes
provider/native allocations and is **not RSS**. Mutable, unstamped contexts are
remeasured; unchanged verified warm contexts reuse their estimate.

## One real browser flow

T3 preview used the built frontend and production FastAPI routes/SQLite, with
`tests/spark_cli/web_cache_browser_fixture.py` replacing only the external agent/
provider boundary. A synthetic profile and a cache count of one were used.

1. Open **SP08 Alpha**: Unicode history and durable answer render; one full-history
   read creates one warmed agent.
2. Send **SP08 warm reuse**: streamed fixture answer renders; provider history has
   exactly two prior messages; full-history reads stay at **one**.
3. Switch to **SP08 Beta**: Alpha's idle resource closes; only Beta remains cached.
4. Return to **SP08 Alpha**: SQLite reload restores the earlier prompt/answer and
   warm follow-up; Alpha creation count becomes two, full-history reads become two,
   and Beta closes.
5. Send **SP08 after eviction reload**: all four prior messages reach the provider;
   the second answer renders and history reads stay at **two**.

The tab and fixture server were closed. This flow ran during implementation;
final generation/lineage/idle-maintenance hardening was then checked with focused
regressions, without a second browser flow. This is browser/HTTP/persistence proof,
not a live model or installed desktop-package claim.

## Matched latency fixture

`web_agent_cache_benchmark.py` compares pinned baseline web/preparation source
from `70eb4602` (production-equivalent to the fixture-only updated foundation)
against SP08. Each mode uses 100 matched sessions, 1000 messages of approximately
2 KiB each, identical Unicode text, route, replayed provider and 5 ms provider
boundary delay. Cold/warm order alternates within each run. The larger sample
followed noisy 24-sample tails; the threshold was not relaxed. A capped acceptance
slot was used. Every serialized request hash matches between baseline/candidate
and against authoritative history. All 100 warm sends perform **zero** full-history
reads; baseline warm sends each perform one.

| Milliseconds (100 samples/mode) | Baseline median | SP08 median | Baseline p95 | SP08 p95 |
| --- | ---: | ---: | ---: | ---: |
| Cold preparation worker + queue | 16.82 | 16.65 | 19.28 | 19.44 |
| Warm preparation worker + queue | 21.44 | 4.26 | 40.72 | 5.13 |
| Cold request entry → first provider callback | 44.43 | 45.51 | 48.57 | 67.07 |
| Warm request entry → first provider callback | 48.87 | 37.82 | 76.50 | 39.96 |

Cold preparation p95 changes **+0.83%**, within the 10% guard; warm preparation
improves. Cold first-token p95 worsened in this run, and smaller batches showed
substantial shared-host tail variance. No general cold TTFT improvement is
claimed. These are fixture callback timings, not live provider/network/browser
first-paint latency. Route/timing projection internals owned by other packets
were not modified.

## 100 real durable large sessions and actual memory

A separate fresh-process `--pressure-only` run writes and reloads 100 real SQLite
sessions, each with 1.05 million Unicode characters, through agent creation and
warm hydration. Candidate context budget is 12 MiB, count cap eight. Baseline uses
the same durable fixture and its existing count-only cap. Values below are bytes;
RSS is independently sampled with `ps`, and traced memory uses `tracemalloc`.

| Measurement | Baseline | SP08 |
| --- | ---: | ---: |
| RSS before cycle | 129253376 | 103268352 |
| RSS after 100 sessions, retained cache | 369180672 | 286474240 |
| RSS after release + GC | 369180672 | 286474240 |
| Retained agent entries (also peak after each cycle) | 8 | 1 |
| Retained logical context estimate | 50405648 | 6300706 |
| Traced Python bytes after cycle | 16827043 | 2120319 |
| Traced Python bytes after release + GC | 16815 | 17431 |

The logical estimate/entry bound passes. RSS grows in both fresh processes and
is not reclaimed after releasing these agents. This does **not** prove bounded
process RSS, a stable long-run RSS plateau, or a causal RSS saving of the difference
between separate processes. Disk history remains authoritative after eviction.
