## Implementation and source revalidation

The base already has durable `runtime_command_receipts`, canonical payload hashes,
compression-family lookup under `BEGIN IMMEDIATE`, and durable web turn projections.
Root create/follow-up paths did not use those receipts. This change extends their
existing transaction with an optional root prompt and initial turn projection;
no new database or migration is needed. Child receipts/retry behavior is unchanged.
Acceptance, prompt/message event, root identity, receipt/event and dispatch intent
commit together. Only `created=True` schedules a task. The same key/body returns
the original session, turn and user-message IDs. A changed payload conflicts.

Optional `submission_id` is supported on ordinary/project create and follow-up.
Create IDs deterministically locate their receipt-owning session, separated by
operation/project route, in the active profile database. Follow-up lookup validates
session existence and resolves compression lineage before looking up a receipt,
and precedes the active-turn rejection. Canonical hashes include prompt, context
references, explicit model/source and operation route; compression aliases do not
change the follow-up route identity. Context array order is significant.

The initially committed projection is uncertain. Registration adopts the committed
turn/message IDs and records its process epoch. Recovery reads label unfinished
root projections from another process uncertain. Receipt retries after process
loss return acceptance and uncertainty without redispatch; terminal persisted
outcomes remain terminal. This guarantees durable acceptance/deduplicated local
dispatch, not exactly-once execution by a remote provider.

Composer transport IDs survive HTTP ambiguity, navigation and tab refresh using
profile/backend-scoped session storage with a memory fallback. Only acknowledged
IDs are retired; existing originating-draft acknowledgement fences remain. The
conversation API helper also covers ChatPage's direct new-chat composers, without
editing ChatPage or SettingsPanel. The mounted composer requests existing recovery
on acknowledgement so a completed replay restores persisted output.

Receipt-backed registration occurs before yielding to another submission, closing
the acceptance-to-active-registration race for distinct sends in one server.
Existing blocking preparation/registration is not optimized here (SP03 owns that).
