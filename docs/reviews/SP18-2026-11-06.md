## Contracts and ownership

`cron/history.py` owns new profile-local `cron/history.sqlite3`: execution receipts, latest-occurrence dispatch guards, and pending manual intent. Definitions, IDs, schedules, timezone calculations, provider routing and jobs.json storage remain in place. The small `trigger_job` hook uses the existing mutation lock and unlocked `_update_job` pattern already used by resume; it commits manual intent before publishing the JSON update. It adds no field to job definitions.

The scheduler owns acceptance/start/execution/delivery settlement. UUID attempt ID and job ID are independent identities; occurrence deduplication and compare-and-set terminal writes fence repeats. Committed execution precedes saved-output writing and delivery. A notification is published only after the first committed delivery settlement; replay does not duplicate a notification. An output-write error cannot turn an already committed successful execution into an execution error. Cancellation errors are cancelled execution; a completed execution followed by Stop remains success with suppressed delivery. Silent, suppressed, empty, no-target, send-error, sent and unknown delivery are distinct. Missing target remains no-target even when the legacy sender returns an explanatory error.

Only a tick holding the existing cross-process `.tick.lock` reconciles abandoned receipts. Accepted/running work becomes interrupted; already committed execution stays success/error/cancelled. Unconfirmed delivery becomes unknown, including a crash after a remote send but before local acknowledgement. Reads never reconcile active workers. An accepted occurrence is not automatically executed again, including one-shots whose next_run_at remains unchanged.

At each tick start, prune settled receipts to the newest 5,000; active/current-tick receipts may temporarily exceed this until the following tick. Compact latest-occurrence guards survive receipt pruning for live jobs; removed-job guards/manual intents are removed at the next tick. Receipt retention does not prune output files. History reads are descending integer keyset pages, default 20, maximum 50, without document bodies. Removed jobs retain receipts until normal pruning. Legacy files do not generate fictitious receipts.

Output references must match the owning job and the existing profile-relative timestamp Markdown layout. Custom/legacy output locations continue writing/delivering but receive no exposed reference. The history drawer delegates to SP17's existing safe viewer, including its no-follow path access, unsupported-platform behavior, pruned-file errors and text-only rendering. The reference is to an existing saved document path, not an immutable content snapshot; existing second-resolution output naming/overwrite semantics are unchanged.

## Crash windows — no cross-store atomicity

- Manual intent commits before jobs.json. A failed/killed mutation can leave unmatched intent; it executes nothing, and later triggering overwrites it. SQLite and jobs.json do not share a transaction.
- Acceptance commits before recurring schedule advancement and execution. A crash before advancement leaves an accepted receipt: the next tick advances scheduling but skips the accepted occurrence. A crash after advancement does not reconstruct missed work. One-shot acceptance fences silent retry.
- Running commits before agent invocation. A crash before/inside execution is interrupted/unknown; no inference that the agent did or did not perform an external side effect.
- Execution commits before output saving/reference attachment. A crash can leave a successful receipt without output, or a saved file without an attached receipt reference. Legacy output browsing remains available.
- Delivery settlement commits after the sender returns. A crash around remote acceptance remains unknown; never infer send success or resend automatically. Existing sender-internal retry/fallback behavior is unchanged.
- Settlement commits before aggregate JSON marking and notification. A crash can leave stale aggregate fields or omit a notification. No exactly-once notification delivery or atomic JSON/SQLite claim; replay intentionally favors no duplicate execution/send over reconstructing uncertain work.

## Limits and rollback

No live provider/send, installed desktop, macOS/Windows package, release, merge or rollout claim. Production inspector's separately reported SP09 1000→1410 failure was not investigated or changed here; these selected gates do not establish all CI green. No ChatPanel, SessionDB, web_server, shared API facade/types, config, Settings, ModelPicker or workspace route edits. No child agents.

Pause affected jobs before rolling back scheduler hooks, especially uncertain one-shots: old scheduler versions lack these replay guards. Preserve the new SQLite ledger and current jobs/output data; do not restore stale jobs.json over newer mutations or delete the ledger to force a retry. Source rollback needs no job-definition migration. Explicit rescheduling/manual trigger is a new occurrence, never a replay inferred from missing history.
