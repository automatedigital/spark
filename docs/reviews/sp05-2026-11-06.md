## Behavior and ownership

A single in-memory store retains at most the three named resources for the current
backend/connection/auth/profile epoch: sidebar metadata, cron summaries, and
Markdown memory targets. It exposes data, updated time, stale state and errors.
It clears/aborts retired scopes, shares in-flight GETs, and gives each consumer an
independent cancellation promise. A mutation/event during an older read fences its
result and reconciles a fresh read. Failures remain stale and retryable without
replacing confirmed data with invented state. No mutation response is cached.

Existing shared SSE delivers invalidations. Successful cron HTTP writes now emit
`bus.cron_changed` after persistence; rejected writes emit nothing. Memory retains
SP21's single parent target read, existing cards, fact browser and review behavior.
Sidebar changes are confined to metadata read/refresh and successful mutation
invalidation. Cron forms/output drawer/schema and shared transport/controllers
remain untouched. No SessionDB/schema, dependency, lockfile, manifest or generated
bundle changes are included.

Focus, reconnect, online and event bursts coalesce over 50 ms. Reference data has a
60-second TTL, with one 60-second fallback tick per mounted resource; fallback
skips hidden/offline pages. A lost event reconciles on a subsequent visible tick
once stale (up to roughly two minutes because ticks and last successful fetches
need not align). Returning online or reconnecting invalidates immediately rather
than waiting for TTL. Committed events do not depend on TTL.

## Performance and actual browser acceptance

The deterministic test replays a literal five-minute visible sidebar + Cron idle
session, with initial reads and the final 50 ms coalescing queue drained. The
baseline uses the committed 15-second polling intervals: **42 requests**.
The candidate invokes the actual resource lifecycle and cache: **12 requests**,
**71.43% fewer**, preserving the assertion of at least 70%. This is fake-clock
request-count evidence, not five minutes of real wall-clock observation.

Chromium exercised the real MemoryPage source fixture through Vite on port 5235
against real memory persistence routes and the existing snapshot/delta/SSE handlers
on an isolated backend at port 9235. Only temporary synthetic `SPARK_HOME` state
was used; no provider or user's live profile was involved. The acceptance runner
was `/tmp/sp05-browser.mjs`; report `/tmp/sp05-browser.json`; screenshot
`/tmp/sp05-browser.png`.

Observed and asserted in one continuous flow:

1. Both memory cards rendered from **one initial `/api/memory` GET**.
2. A simultaneous focus/online/focus burst plus bus wake caused **one** refresh.
3. Chromium network offline mode hid a committed external mutation; reconnect
   recovered and displayed it without manual refresh.
4. A subsequent external mutation reached the visible card via real SSE in
   **82 ms after HTTP acknowledgement** (87 ms from mutation request start),
   below the one-second acceptance bound.
5. Adding an entry through the rendered UI persisted it in the real backend;
   the subsequent invalidation/read completed. No page errors occurred.

Preview initially showed the real cards and a live SSE update in 59 ms. Its
visibility override failed twice with `Cannot redefine property: visibilityState`,
so the completed recovery acceptance used normal Chromium network controls.
Visibility suppression and TTL/lost-event timing are covered by the deterministic
lifecycle regression rather than claimed as real OS background-tab measurements.
