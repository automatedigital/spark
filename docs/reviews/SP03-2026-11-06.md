## Change and ownership

`chat_preparation.py` owns an eight-admission guard covering queued/running
preparation, per-session request serialization, worker handoff, bounded timing
samples, and explicit preparation/result dataclasses. It submits to the existing
runtime executor; no worker counts or pools were added. Saturation is HTTP 503
with Retry-After and an actionable message, before durable acceptance. Cancelled
HTTP waiters retain admission while their worker still runs.

Create/send/warm move lineage/SQLite reads, context file validation/persistence,
routing/configuration, and agent/client initialization off the API event loop.
Transient DB connections open/read/close in their worker. Follow-up records the
prior history length before acceptance and excludes the eagerly accepted prompt
from hydration, preserving the original prompt prefix and one-prompt dispatch.
Routing and custom provider resolution still use the existing server services.

An accepted turn exists in `starting` before expensive history/client preparation.
Stop fences both the preparation boundary and execution-worker queue boundary.
Task cancellation joins uncancellable preparation before releasing ownership.
Warm workers serialize with sends. Follow-up emits the existing initializing-agent
status while preparing. The small optional `interrupted` pass-through in the
existing completion helper preserves an interrupted outcome for these stopped
preparations; no recovery API fields, read routes, SessionDB schema, migration,
receipt, or dispatch-intent contracts changed.

The existing cached AIAgent's persistent SessionDB lifetime is unchanged. This
patch proves worker ownership for transient preparation connections; it does not
prove that every cached-agent DB connection across every later runtime operation
is created/used/closed on one physical worker. The packet's stricter connection
requirement therefore remains incomplete. Finishing physical cached DB affinity
requires cache/agent creation, disposal and title/runtime lifetime changes outside
the assigned preparation slices. A generic proxy was not introduced: delegation
relies on actual SessionDB identity and would require its own lifecycle evidence.

This is demonstrated, not hypothetical: the standalone real-SQLite
`tests/spark_cli/chat_preparation_db_probe.py --output /tmp/sp03-db-ownership.json`
exits **1**. Its fake agent/provider makes no account request. The cached DB is
created on `spark-runtime-worker_0`, actually queried on `spark-web-turn_0`, then
closed on `MainThread`. The complete trace is retained in the samples JSON.
This failed explicit ownership gate blocks publication even if the ordinary
regression suites pass. No failing test was skipped, softened, or hidden.

No frontend implementation, shared configuration, lockfile, manifest, PLAN,
tracker state, or production bundle is included. Build-generated bundle changes
were restored after browser checks; the tested build is retained locally at
`/tmp/sp03-built-web`.

## Integration, limits and rollback

Rebase/integrate the eventual SP02 recovery implementation explicitly, preserving
its response fields, then repeat shared lifecycle/browser checks. No acceptance
claim is made for that integration, native macOS/Windows packages, live providers,
first-token latency, or the pre-acknowledgement Stop race.

Rollback is a scoped source revert with no schema rollback. Stop admission and
drain/reconcile owned workers first; keep SP01 durable receipts/intents and treat
uncertain accepted work as uncertain. Never replay an accepted prompt to restore
UI state. Do not restore an older user database.
